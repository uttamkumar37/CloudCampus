# Migration Graveyard

This file documents Flyway migrations that ran in a dev/CI environment but **did not produce the data they were intended to** because their guard clause failed. They remain in the chain (with Flyway-recorded checksums) and **must not be edited or deleted** — that would break Flyway validation on every existing database.

If you want their effect, see the replacement migration listed under each entry.

---

## V42 — `jnv_lucknow_seed`

- **Intended:** Seed JNV Lucknow demo data (560 students, 22 staff, etc.) under tenant `aaaaaaaa-0000-0000-0000-000000000001`.
- **Why it skipped:** Tenant `aaaaaaaa-...` is a hard-coded fantasy UUID that was never produced by the bootstrap path. The guard at the top of the script returns immediately when this tenant is absent.
- **Replacement:** Seed is now performed by `TenantBootstrapService` (programmatic) for the real tenant `c0000000-0000-0000-0000-000000000001`, plus V58 (which uses the historically-bootstrapped UUID `804d7650-...`), plus V91 (which targets `c0000000-...`).

## Rules for future graveyards

- **Never edit a checkmarked migration.** Flyway validates checksums on every run. Editing a recorded migration breaks every database that already ran it.
- **Never delete a checkmarked migration.** Flyway will complain that an applied migration is missing from disk.
- **Always add a replacement migration with a higher version number.**
- **Always update this file** when you knowingly create a no-op migration so the next person reading the chain understands why.
